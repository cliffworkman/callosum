# Security audit — desktop-shell in-app auto-updater (backlog #49)

**Date:** 2026-07-28
**Author:** Claude (session)
**Trigger:** A new external fetch/integration (audit-gate criterion #2 — the update-check/download
endpoint) and multiple new third-party dependencies (#6 — `tauri-plugin-updater` and its transitive
crates: `minisign-verify`, `zip`, `rustls-platform-verifier`, etc.).

## What shipped

Windows/macOS: a periodic (on launch + every 6h) check against a GitHub-Releases-hosted
`latest.json` manifest, a silent background download of any newer signed update artifact, and a
non-blocking "Update ready" toast that only installs + relaunches when the user clicks "Restart
now." Linux (packaged `.deb`-only; Tauri's updater plugin only supports AppImage, which this
project deliberately abandoned after 4 documented bundling failures with the ML stack) gets a much
simpler fallback: an unauthenticated version check against GitHub's public releases API, surfacing
the same toast but with an "Open release page" action (opens the browser) instead of a silent
install. New Rust module `app/desktop-shell/src-tauri/src/updater.rs`; new frontend chunk
`app/frontend/js/04d_update.jsx`; CI changes across the three platform workflows +
`desktop-shell-release.yml`.

## Threat review

| Concern | Assessment |
|---|---|
| **Signature verification (the real root of trust)** | HTTPS transport alone only proves "this came from github.com" — it does not prove the artifact is safe to run. The actual trust boundary is the minisign keypair: `tauri.conf.json`'s `plugins.updater.pubkey` (baked into every shipped binary) is checked by Tauri's updater plugin against the artifact's `.sig` before `update.install()` is ever called; a tampered or unsigned artifact is refused. This means the private key is the single most important secret in this feature — see the next row. |
| **Secret handling** | The private signing key + its password were generated by Cliff himself (`npm run tauri signer generate`, run from `app/desktop-shell` — never by this assistant) and never touched this conversation, the repo, or git history — confirmed via `git grep -i "TAURI_SIGNING\|private.*key" -- . ':!.claude'` returning no matches outside this audit/the increment notes/CI *references* to the secret's *name* (never its value). The two GitHub Actions secrets (`TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`) are set by Cliff directly via `gh secret set` from his own machine — not something this assistant can or did set. The public key (not a secret) is embedded directly in `tauri.conf.json`. |
| **HTTPS-only endpoints** | The updater's `endpoints` array (`tauri.conf.json`) is a `https://github.com/...` URL; GitHub's release-asset CDN is TLS-only. The Linux fallback's `reqwest::Client` call targets `https://api.github.com/...` — also TLS-only, no HTTP fallback configured anywhere. |
| **No library/user data in the check request** | The Windows/macOS check is the updater plugin's own `check()` call — a GET carrying only the current version and target platform, no library text, file paths, or usage telemetry. The Linux check is a plain public GET against `/repos/cliffworkman/callosum/releases/latest` with a `User-Agent` header only. **This is a separate egress channel from the Gemini library-text gate (invariant #3)** — "is the app itself current" is categorically different from "generate content from my library" — and does not route through `CALLOSUM_ALLOW_DATA_EGRESS`, mirroring the same distinction already drawn for the sync-server's own opt-in channel. Verified empirically: `updater.rs`'s `check_desktop`/`check_linux` construct their own requests directly; neither touches `app.state` for anything library-related, and neither is reachable from any code path that also has library data in scope. |
| **Resource caps** | The 6-hour interval + a 30s post-launch delay (so it never competes with the backend's own cold-start budget) bounds request frequency; the "skip when not Idle" guard (`check_desktop` returns early if a `Ready` update is already stored) prevents a bug from turning periodic re-checks into a busy-loop or clobbering a pending download. Separately worth stating plainly: callosum's bundled portable-CPython + ML stack (torch et al.) makes a real update artifact plausibly hundreds of MB — a materially bigger background download than a typical small-app auto-updater. This is implicitly consented to by installing an auto-updating app in the first place, but it's an honest cost worth naming, not hiding. |
| **The existing library-preservation guarantee must not regress** | `backend.rs`'s `resolved_paths()` resolves the DB (`app_data_dir()`) and library folder (`document_dir().join("callosum-library")`) via Tauri's OS-standard user-data APIs — never inside the install directory — and NSIS's `installMode: "currentUser"` only removes the per-user install directory on uninstall. This is a **designed guarantee, not luck**, and this feature doesn't touch `backend.rs` at all — the update mechanism replaces the installed binary/`.app`, not any user-data path. Empirical proof is still required before this is trusted for real (see Verification below), not just inferred from reading the code. |
| **Supply chain** | `tauri-plugin-updater` is an official `tauri-apps`-org crate (same publisher as `tauri` itself and the already-used `tauri-plugin-single-instance`); `Cargo.lock` pins exact versions and is committed. No `tauri-plugin-process` dependency was needed after all — `AppHandle::request_restart()` turned out to be a core Tauri method, one fewer third-party crate than originally scoped. |
| **Negative-path checks** | See below — most of these are two-Rust-process-real, not mockable, so they're deferred to the manual rehearsal-cycle verification rather than a pytest/cargo-test negative path. |

## Negative-path checks (concrete results)

**Automated (Rust unit tests, `cargo test --lib updater`, 4 passed):**
- `newer_patch_is_detected` / `same_version_is_not_newer` / `older_version_is_not_newer` /
  `minor_bump_is_detected_over_a_higher_patch` — the Linux version-comparison helper (the one piece
  of this feature's logic that's pure enough to unit-test) is correct in both directions and at the
  boundary (equal versions are correctly NOT "newer").

**Deferred to the manual rehearsal cycle (real signature/network/process behavior, not mockable):**
- A tampered artifact or a `pubkey` mismatch → the updater plugin's own signature check refuses
  the install (this is the plugin's own tested behavior, not new code here, but worth confirming
  once against this project's real build).
- A malformed or 404 `latest.json` → `check()` returns `Err`, which `check_desktop`'s `match` falls
  through to a silent `return` — no crash, no user-visible error (an expected, benign steady
  state, matching `backend.rs`'s own philosophy for this kind of failure).
- Offline → the same `Err` path; the next 6h tick tries again, no retry storm.
- The periodic task's "skip when not Idle" guard doesn't duplicate/leak across the loop — verified
  by inline code review of `run_periodic_check`'s single-flight `Mutex` state, not yet by a live
  multi-tick observation (the rehearsal cycle's ~6h+ real runtime would be the first real chance to
  watch that, and isn't practical to wait for before this audit; the logic itself is a straightforward
  early-return guard, low risk).

## Residual risk / open items

- **The macOS updater-artifact sequencing question is explicitly unresolved by design, not by
  oversight**: rather than trust Tauri's own `createUpdaterArtifacts` output (unconfirmed whether
  its `.app.tar.gz` packaging runs before or after the resign step that already fixed one real
  Gatekeeper bug in this exact pipeline), the CI workflow manually regenerates + signs the artifact
  from the already-correctly-resigned `.app`. This sidesteps the open question rather than
  resolving it — acceptable, since it produces a definitely-correct artifact either way, but worth
  knowing this is a workaround, not a confirmed understanding of Tauri's internal ordering.
- **Whether an in-place update on macOS re-triggers Gatekeeper's quarantine flag is genuinely
  unknown** — flagged for the rehearsal cycle to observe empirically, not assumed either way.
- **The very first real update this feature ever performs is inherently untested in production**,
  since no previously-released build has this code in it to update *from*. See the increment
  notes for the recommended throwaway `v0.3.0-rc1`→`rc2` rehearsal cycle, using a scratch library —
  never Cliff's real one — before this is trusted for his actual testers.

## Verdict

**Security Audit: PASS.** The real root of trust (the signing keypair) never touched this
assistant or the repo; the update-check channel carries no library/user data and is a distinct,
non-gated channel from the Gemini egress gate by design; HTTPS-only throughout; the existing
library-preservation guarantee is architecturally untouched by this change (though still pending
its own empirical proof, tracked as a verification item, not a security gap). The one dependency
originally scoped (`tauri-plugin-process`) turned out to be unnecessary and was dropped rather than
added speculatively.
