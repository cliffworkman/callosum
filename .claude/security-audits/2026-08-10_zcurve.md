# Security audit — z-curve (collection-level expected replication/discovery rate)

**Date:** 2026-08-10
**Status:** complete — PASS

## Scope

`app/backend/api/routers/methods_zcurve.py` — a new endpoint pair mirroring the already-audited p-curve pattern
almost exactly: `POST /methods/zcurve/run` (async job over a user-selected paper set, reuses the statcheck
extractor) + `GET /methods/zcurve/run/{job_id}` (poll). Ephemeral — no persistence, no new table/migration.
`app/backend/methods/zcurve.py` is pure local computation (numpy/scipy EM fit + bootstrap), no I/O of its own.
Written to confirm the mirroring, not re-derive the p-curve threat model from scratch.

## Principles-gate note (rule #9)

Backlog #55's original framing (an LLM extracting each study's "focal statistic," the source design doc's own
words: "more dangerous... judgment-laden") was declined outright. The shipped design instead extends p-curve's
already-proven pattern: statcheck's exhaustive, deterministic significant-test extraction, zero LLM, zero egress.

The new consideration beyond p-curve: EDR/ERR are quantitative *rate* estimates, more tempting to misread as
describing the specific selected studies than p-curve's abstract right-skew statistic. Mitigated at the design
level (not a security boundary, but recorded here since it's the audit's other half of "what could go wrong"):
a hard (not dismissible) reliability warning below the reference implementation's own N=300 threshold, CIs always
rendered beside the point estimate, and no per-paper/per-author breakdown anywhere in the response or UI — only
the aggregate + the already-precedented `included_tests` list (paper/page/z/raw, exactly like p-curve).

## Threat review

- **Input validation:** `paper_ids` de-duplicated, order-preserved, capped at `MAX_ZCURVE_PAPERS = 1000` (mirrors
  `MAX_PCURVE_PAPERS`, rule #4); empty selection → 422 before any job is created.
- **Output encoding / injection:** parameterized SQLAlchemy Core throughout (rule #3, via the reused
  `get_chunks_for_paper`/`list_live_paper_ids` repository calls); the response is a plain pydantic model of
  floats/strings — no raw user text is interpreted as markup or executed.
- **Authorization scoping:** trashed papers are excluded (`list_live_paper_ids` filter, same as p-curve); a job
  belongs to its own `job_id` in `zcurve_jobs` — no cross-job data leak (the `JobStore` pattern already used
  library-wide).
- **SSRF / external calls / data egress:** none — `methods/zcurve.py` imports only `numpy`/`scipy.stats`
  (already-vetted, pinned dependencies used elsewhere in this exact module family); the EM fit and bootstrap
  never make a network call. No LLM, no external API.
- **Resource caps:** the paper-count cap bounds the extraction; the EM fit itself is bounded by `MAX_ITER=500`
  per restart × `N_RESTARTS=8` for the initial fit, and `N_BOOT_DEFAULT=400` bootstrap replicates (each a single,
  warm 1-restart fit) — a real performance bug was caught and fixed during implementation (an absolute
  log-likelihood convergence criterion never converges for large N, so every fit burned its full iteration
  budget; replaced with a scale-invariant parameter-change criterion). A stress test against ~7,000 significant
  z-values completed in ~57s as a background job after the fix (previously hung indefinitely) — acceptable for
  an async, Status-tracked operation, and far above any realistic personal-library selection.
- **Bypass surface:** no new dependency (numpy/scipy already vetted); no auth gate of its own, matching p-curve's
  own posture (a local-only tool with no sensitivity beyond normal library data).
- **Data exposure:** the response carries only aggregate statistics + the same per-test provenance p-curve
  already exposes (paper id/page/raw text/computed value) — no new sensitive surface.

## Negative-path checks

Verified by `tests/test_zcurve.py` (7 passed):
- Empty selection (no significant results) → honest `None` EDR/ERR + explanatory note, no crash.
- `fit_zcurve([])` → `None` cleanly (no divide-by-zero, no NaN propagation to the API layer).
- A live API run with a fake job id → 404; an empty `paper_ids` POST → 422.
- The power formula independently verified against the reference `zcurve` R package's own documented component
  powers (not assumed from memory).
- The EDR/ERR recovery verified against a synthetic dataset with a *known* generating distribution (both land
  within 0.05 of the true value, and the CI brackets the true value) — a correctness check, not just a shape
  check.

Live-verified end-to-end via Playwright against the real 217-paper curated library (server restarted to pick up
the new backend code): the reliability warning rendered correctly for a real 15-paper/76-significant-test
selection; zero console errors across the full flow (select → run → poll → expand included tests → credit-add →
verify via `POST /library/credit/status` → clean up the test-added paper via `DELETE .../permanent`).

## Result

No exploitable issue or new sensitive boundary was found. The endpoints reuse the already-audited p-curve
pattern's exact shape; the only genuinely new considerations were (1) a real performance bug in the EM
convergence criterion, caught and fixed before shipping, and (2) the rate-estimate framing risk, addressed at
the design level per the Principles-gate note above.

**Security Audit: PASS**
