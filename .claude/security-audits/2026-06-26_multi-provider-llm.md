# Security audit — multi-provider LLM engine (inc 149)

**Date:** 2026-06-26
**Trigger (audit gate):** new external fetches (OpenAI + Anthropic chat APIs); a new outbound path (a local
OpenAI-compatible endpoint); a change to the data-egress gate. No new third-party dependency (httpx is already a dep).

## What it does

Introduces one provider-neutral `complete(config, prompt)` seam (`app/backend/llm/providers.py`) that all six LLM
generators route through. `config.provider` ∈ `gemini` (google-genai SDK) / `openai` / `anthropic` / `local`
(httpx). The `local` provider is the flagship: summaries generated by a model on the user's own machine, with
**zero egress**.

## Threat review

- **Egress invariant (#3) — extended correctly, not weakened (PRINCIPLE-LEVEL; see the Principles write-up in
  `INCREMENT-149-NOTES.md`).** Cloud providers (`gemini`/`openai`/`anthropic`) still require explicit egress
  consent: `requires_egress(provider)` is True for them, so the `EgressGated*` wrappers (and the generators'
  defense-in-depth self-checks) raise `DataEgressDisabledError` exactly as before when egress is off (tested:
  cloud + egress-off → blocked). The `local` provider returns `requires_egress("local") == False` — but ONLY
  because a local endpoint is **loopback-restricted**: `complete()` rejects any `local` `base_url` whose host is
  not `127.0.0.1`/`localhost`/`::1` (and inc 150 will 422 a non-loopback base_url at the settings-write boundary).
  So "local ⇒ no egress" is **honest**: text never leaves the machine. The invariant protects *data leaving*; a
  loopback model keeps it on the machine, so consent-to-egress is correctly N/A. The misaligned easy path —
  allowing an arbitrary `base_url` under the "local, no-egress" label (data could leave) — is **declined**
  (loopback enforced in `complete()`, tested: non-loopback local → `ProviderError`).
- **SSRF.** The only user-supplied URL is the local `base_url`; it is constrained to loopback hosts before any
  request. The OpenAI/Anthropic hosts are **constants** in code (`https://api.openai.com`,
  `https://api.anthropic.com`) — not request-derived.
- **Secret handling (per provider).** Each provider's key is read via `config.resolved_api_key()` and passed only
  to the provider call (Bearer header / `x-api-key` / genai client). Keys are **never logged**; every provider
  error is **redacted** (`_redact` → `str(exc).replace(api_key, "***")`) and length-capped before it reaches a
  job error / `detail`. Keys live in the gitignored `~/.callosum/app-settings.json` store under per-provider
  fields (`api_key` [gemini], `openai_api_key`, `anthropic_api_key`); `GET /settings` still returns status only.
- **Input validation / fail-closed (rule #4).** httpx calls set a 60s timeout; non-2xx → `raise_for_status` →
  `ProviderError` (the response body is truncated to 200 chars + redacted); malformed JSON / missing fields →
  `ProviderError("Malformed … response")`. No 500s leak out (the async jobs already wrap exceptions).
- **Resource caps.** One bounded call per request; Anthropic gets an explicit `max_tokens` (2048).
- **Supply chain.** No new dependency (httpx already used for metadata APIs; genai already a dep).

## Negative-path checks

- cloud (openai/anthropic/gemini) + egress OFF → `DataEgressDisabledError`. ✅ (test)
- local + loopback base_url + egress OFF → generates (no raise). ✅ (test — the headline guarantee)
- local + non-loopback base_url → `ProviderError`, no request sent. ✅ (test)
- a provider error containing the key → key redacted from the message. ✅ (`_redact`, exercised)
- per-provider key resolution picks the active provider's key. ✅ (test)

## Result

**Security Audit: PASS.** (inc 150 adds the Settings provider UI + the settings-write loopback 422; this audit
covers the engine + the loopback enforcement in `complete()`.)
