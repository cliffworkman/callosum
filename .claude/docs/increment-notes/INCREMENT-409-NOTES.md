# Increment 409 — In-app auto-updater for the desktop shell (backlog #49)

## Implemented

Two Mac colleagues (one AI-skeptic, one AI-enthusiast) had already filed the first bug reports
against the public v0.2.0 installer, and Cliff wanted patches to reach them without asking anyone
to re-download and reinstall by hand each time — "like Spotify": check automatically, download
silently, prompt (never force) a restart once ready.

**Windows/macOS — the real Spotify-style flow:**
- New `app/desktop-shell/src-tauri/src/updater.rs`: a periodic check (30s post-launch delay, then
  every 6h) via Tauri's official `tauri-plugin-updater`. On finding an update, silently
  `update.download(...)` (no UI — the "pushed automatically" half), store the `Update` handle +
  downloaded bytes in a managed `UpdateState`, and emit a small `"update-ready"` Tauri event. A
  "skip when not Idle" guard means a later periodic tick never clobbers a `Ready` update still
  awaiting the user's click. `install_update_now` (a `#[tauri::command]`) installs the stored bytes
  and calls `AppHandle::request_restart()` — a **core Tauri method**, discovered mid-build to make
  the originally-scoped `tauri-plugin-process` dependency unnecessary (one fewer third-party crate
  than planned). `request_restart()` triggers the exact same `RunEvent::ExitRequested`/`Exit` that
  `lib.rs` already handles to kill the backend child process — no new cleanup path needed for the
  restart case.
- `tauri.conf.json`: new `plugins.updater` block (the real public key, generated by Cliff himself
  via `npm run tauri signer generate`, run from `app/desktop-shell` — never by this assistant),
  `endpoints` pointing at the stable `.../releases/latest/download/latest.json` alias, `windows.
  installMode: "passive"` (an unobtrusive progress indicator during the actual install, without a
  second click — `basicUi` would demand one, contradicting "never forced" once the user already
  clicked "Restart now"). `bundle.createUpdaterArtifacts: true` so `tauri build` also emits the
  signed `.nsis.zip`/`.app.tar.gz` artifacts the JS-invisible Rust-side `check()` consumes.

**Linux — an honest, simpler fallback, not silent auto-update:** Tauri's updater plugin only
supports AppImage on Linux; this project's Linux build is `.deb`-only (AppImage was explicitly
abandoned after 4 documented bundling failures with the ML stack — not worth reopening for this).
`updater.rs`'s Linux path does a plain unauthenticated `GET /repos/.../releases/latest`, compares
`tag_name` against the running version via a small pure `is_newer`/`parse_version` helper, and
emits the same event with `action: "open-page"` — the shared frontend toast renders "Open release
page" (spawns `xdg-open`) instead of "Restart now." `tauri.linux.conf.json` explicitly sets
`createUpdaterArtifacts: false` (an explicit override, not just trusting the base `true` gets
silently ignored, given the documented AppImage scar tissue).

**The one architectural correction that reshaped the whole design:** the frontend build pipeline
(`app/backend/api/frontend.py`) runs esbuild in transform-only mode — no `--bundle`, no entry file
— so `import { check } from '@tauri-apps/plugin-updater'` would pass through untouched and fail at
runtime; this project's `package.json` has never carried a runtime npm dependency. **Fix: the
entire lifecycle lives in Rust**; the frontend's only new surface (new `app/frontend/js/
04d_update.jsx`) is one event listener + one `invoke()` call via the already-enabled
`window.__TAURI__` global (`withGlobalTauri: true`, confirmed already set in `tauri.conf.json`) —
zero new frontend npm dependencies.

**Frontend UI:** `UpdateNotice` renders nothing until an `"update-ready"` event fires, then a
free-floating `position: fixed` toast (bottom-right — `.pdf-toast`'s existing error toast is
bottom-center, so the two can never collide), using the existing canonical `.btn.btn-primary`/
`.btn.btn-ghost` button classes. "Later" collapses it to a small persistent `--accent`-toned pill
(reachable again on click) rather than discarding it. Mounted once, globally, at `40_app.jsx`'s top
level (beside `AccessLockOverlay`) — **not** inside `04b_workspaces.jsx`'s menu bar, since
`.menubar`'s `overflow-y: hidden` (the exact bug the Status popover hit and fixed via a portal,
inc 406) would have clipped a toast hanging below it; this component was simply never inside that
ancestor to begin with, so no portal is needed here.

## Addendum — four real CI bugs found only by actually pushing (same day)

Local verification (`cargo check`/`cargo test` on Windows) came back clean, but that only proves
the Windows-compiled code paths — the platform-conditional (`#[cfg(target_os = "linux")]`, `#[cfg
(any(target_os = "macos", windows))]`) code can't be fully exercised from one dev machine. Pushing
immediately surfaced four real issues across the three CI runs, each found from actual job logs
and fixed same-session:

1. **macOS workflow failed to even parse** ("Unrecognized named-value: 'secrets'") — GitHub
   Actions doesn't allow the `secrets` context in a step-level `if:` condition. Fixed by moving the
   skip-when-unsigned check into the shell script itself (checking the already-injected env var)
   instead of a workflow-level `if:`.
2. **Linux failed to compile**: `reqwest::Response::json()` needs the crate's `"json"` feature,
   never enabled. Confirmed: this code is `target_os = "linux"`-gated, so the earlier "0 errors"
   `cargo check` on this Windows machine never actually compiled it — a real gap in that
   verification, only caught by CI running on a real Linux runner. Fixed by adding `"json"` to
   `Cargo.toml`'s `reqwest` features.
3. **Windows/macOS builds failed**: GitHub Actions sets a referenced secret's env var to an
   **empty string** (not absent) when the secret doesn't exist yet — Tauri's bundler treated
   "present but empty" as "a key was given" and tried to decode `""`, failing the whole build
   rather than skipping signing. First fix attempt: `unset`/`Remove-Item Env:\` the vars when
   blank.
4. **Still failed after fix #3**: `tauri.conf.json` already has a real public key baked in
   (`plugins.updater.pubkey`) — even with the env vars genuinely absent, Tauri demands a matching
   private key unconditionally ("A public key has been found, but no private key"), since a pubkey
   with no private key ever available is a broken config, not "signing is optional." **Real fix**:
   when unsigned, pass `-c '{"bundle":{"createUpdaterArtifacts":false}}'` to `tauri build` for that
   build only (never editing `tauri.conf.json` itself) — an honestly-unsigned build with no updater
   artifact, not a hard failure. This branch stops firing the moment Cliff sets the two real GitHub
   secrets.

All three platforms (Windows, macOS, Linux) are green as of this addendum, still unsigned (secrets
not yet set) — confirming the whole pipeline builds and verifies cleanly end-to-end even before
Cliff's own remaining manual step.

## Addendum 2 — v0.3.0 shipped for real the same night, two more real bugs found and fixed live

Cliff set both `TAURI_SIGNING_PRIVATE_KEY`/`_PASSWORD` GitHub secrets the same session, and — since
the feature is genuinely low-stakes right now (his own words: "n = 3 max, including me," and
nobody's been told to update yet) — chose to skip a throwaway rc1/rc2 rehearsal and ship the real
`v0.3.0` directly (the version bump: `chore(release)` commit, tag `v0.3.0`, real release notes).
The full tag-triggered release pipeline ran clean end to end — all three platforms, real signing,
`latest.json` published — but two more real bugs surfaced only by inspecting the actually-published
release, both fixed live before calling it done:

1. **The release body showed the last commit's message, not the annotated tag's message.** `git
   tag -l --format='%(contents)' "${{ github.ref_name }}"` didn't return the real tag body on the
   runner the way it does locally — not yet root-caused (a `actions/checkout` tag-fetching
   nuance is the leading suspect). Worked around by hand for this release
   (`gh release edit --notes-file` with the real tag message read locally); the underlying
   workflow step is unchanged and will need a real fix before the next release, or every future
   release body will have the same problem.
2. **macOS's `latest.json` pointed at the wrong artifact.** `createUpdaterArtifacts: true`
   produces its OWN auto-signed `Callosum.app.tar.gz` (no version/arch in the name) *in addition
   to* the manually-regenerated, trusted `Callosum_0.3.0_aarch64.app.tar.gz` this workflow
   deliberately creates instead (see the main entry above — the ordering-relative-to-resign
   question was never resolved, just designed around). `ls dist/*.app.tar.gz | head -1` picked the
   untrusted one alphabetically. Fixed live: rebuilt `latest.json` by hand from the already-correct
   published signature, deleted the stray untrusted asset from the release, and fixed
   `desktop-shell-macos.yml` to delete Tauri's own auto-generated artifact right after the manual
   regen, so this can't recur on the next real release.

**v0.3.0 is now live and correct** (verified: `latest.json`'s macOS entry points at
`Callosum_0.3.0_aarch64.app.tar.gz` with its matching signature; the release body is the real
release notes). Cliff's own current install is a `v0.2.0` copy with no updater code — it (and
his two testers') will need one final manual reinstall to cross into `v0.3.0`; every release
after this one should update itself. **Not yet done**: a real live test of the actual update
*mechanism* (does a running v0.3.0 detect and offer a hypothetical v0.3.1) — that only happens
naturally whenever the next real patch ships.
